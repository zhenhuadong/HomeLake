
# 经理职位的核心能力
面试经理职位的核心是要候选人展现：技术深度，领导能力，战略思维和人员管理技巧。

## 技术与决策能力
### Q1：如何评估技术方案(技术选型和技术栈，比如Appian）？
- 考查点：技术判断力，风险评估，权衡能力
- 回答思路：需求分析（性能/成本/团队能力），PoC(Proof of Concept)验证，技术债评估。
- 回答例子：DOT项目是处理交易上线的，具有低频，高价值的特征。业务以审批流程为主。
  - 业务痛点包括，
    - 审批过程需要知道上下游系统中的数据（信息和状态），比如 
      - 需要从CRM获取（Deal是否处于win状态，交易的法律实体有哪些，Sales support是谁？等等）
      - 需要从CitiKYC获取 参与交易的法律实体的KYC状态
      - 需要从CitiScreening获取 参与交易的人员是否在制裁名单中
      - 需要从Flexcube获取 账号创建状态
      - 需要将上线数据，同步到老的系统ATIS中
      - 需要将交易文档（Contractual）存储在DMC系统中，非交易文档（Ancillary）存储在S3上。
      - 需要将交易上线相关的数据存储到数据库
    - 审批流程需要多角色参与（Transaction manager， Client service， TIM team， Sales support 等等）
    - 交易上线数据golden source 新老系统迁移，老系统各个region又不相同
  - 用户希望保留自己参与流程定制开发和生成新报表的能力，他们熟悉Appian低代码技术
  - Appian PoC验证和技术债评估
    - Appian低代码技术本身擅长快速开发交付流程，已经有一些小的项目使用该技术，POC和技术债评估已经完成
    - 花旗是该技术的战略合作伙伴。
    - 本身或者通过插件可以支持上下游系统使用的HTTP/S3/Kafka/JDBC等接口协议。
  - 项目属于Digital First 项目集中的一部分，用户需要一个快速可见的一个应用来决定是否给该项目预算。
  - 我们选用了Appian技术栈（包括Excel，Kafka等插件）来连通上下游和处理上线流程，选用Java技术栈来连通现有的上线系统（ATIS）。
  - 我们组建了London的Appian开发团队和上海的Java开发团队，并在3个月内交付了MVP0。6个月内交付了具有完全EMEA Deal onboarding功能的MVP1。并在后续每个月完成一次交付，解决现有功能的缺陷和实现新的功能。一年内交付了APAC/EMEA Deal onboarding全部功能。
### Q2：如何遗留系统？
- 考查点：重构策略和风险控制
- 回答思路：分阶段重构，自动化测试保障，业务价值优先
- 回答例子：DOT项目在APAC deal onboarding开发阶段的重构。
  - 业务流程重构：APAC 和 EMEA有许多类似的功能，但是在某些阶段又有所不同，APAC和EMEA相同角色有不同的团队，也有一些团队的职责有重叠和交叉。这一业务现状导致了，我们必须理解用户现有流程不同，团队不同和职责差异的原因，进而梳理出标准的deal onboarding流程。
  - 平台重构迁移：Appian 平台不能有效的隔离资源，Deal onboarding作为最复杂和最重要的应用占用了贡献平台一半以上的资源。需要迁移到自己的专有平台上。
  - 架构重构：Appian擅长低频和流程审批等，却不擅长大数据量或高频的操作，所以需要将高频的操作剥离，使用Java技术栈来构建这些高频或大数据量的domain service。
  - 代码重构：Appian的版本管理是基于环境的代码版本管理，可重用的Object和Role based objects区分管理。构建Hierarch的Appian objects.
  - 重构基于业务需要来决定优先级，比如架构重组，往往同时解决现有问题或者实现新的功能，Kafka domain service 解决了用户在上下游系统的数据延迟问题，CitiKYC domain service 实现了大量同步KYC状态的功能节省了用户大量的手动触发动作。比如代码重构，往往是因为标准流程中对APAC和EMEA现有流程的增强，因此将重用的代码剥离出来，特殊流程管理。避免引入开发一个新功能破坏一个现有的功能。比如平台的迁移，同时绑定了用户需要的SSO功能。
  - 重构需要自动化测试来保障质量，自动化测试集分级，每天跑最核心的功能测试集，每个sprint跑和新功能相关的测试集，和每个release跑全量的功能测试集
### Q3：如何推动技术质量（CICD/代码规范？
- 考查点：工程文化塑造能力
- 回答思路：通过自动化工具（SonarQube）+ 代码评审流程 + 质量指标纳入KPI
- 回答例子：针对Java技术栈通过SonarQube + Blackduck + SAST 等Citi选定的代码和第三方包的自动扫描工具。针对Appian，因为无成熟的自动化评审工具，还需要通过人工的方式评审，通过引入代码规范和必要的设计模式，并确保人人都熟悉并能符合这些要求，进而达到人人都可以初步的peer review。


## 团队管理与协作
### Q4 如何提升团队效率？
- 考查点： 流程优化能力
- 回答思路： 识别瓶颈（价值流分析），引入敏捷实践（看板），减少会议和文档负担
- 回答例子： DOT项目三大瓶颈：第一、team velocity 产出不够；第二、大量需求积压；第三、跨时区交流障碍；通过价值流分析可以得出，主要原因有两个：
  - 人员配置不协调： 
    - 地理位置不协调：PO都在London+BA都在Dublin+Arch在北美；开发+测试都在上海和印度。时区问题导致天然沟通障碍。
    - 人员配比不协调：4个PO+3个BA并行梳理需求，导致需求过多，且所提的方案没有经过技术团队充分的review，进而导致团队无法处理大量低质量的需求积压。
  - 减少一个PO和一个BA，并调整一个BA到印度时区。基于团队产出和目前需求量和客户沟通排期，减少并行处理需求量。集中精力和资源，处理最有价值的用户需求。从而减少碎片化交付，和避免频繁切换交付的功能模块带来测试压力。
### Q5 如何处理团队成员的冲突？
- 考查点： 情商和解决问题的能力
- 回答思路：私下沟通+厘清根源+促进共识+跟进结果
- 回答例子：开发团队在和PO的沟通中识别出一个紧急的高价值低改动需求。开发团队认为代码改动只有一行，如果不改动可能会导致上游新功能破坏DOT应用的一个主要功能。测试团队考虑到测试排期，工作负荷，和临近交付，不同意修改当前的发布包。双方各执己见，互不信任。后续通过让QA参与方案和代码的review，同时让开发参与设计相关测试用例，让双方理解彼此的立场和原因。最后以很小的成本和实践周期交付了高价值的功能。后续也同步改进了fast feature的相关流程。
### Q6 如何激励技术骨干
- 考查点：人才保留策略
- 回答思路： 技术挑战性的任务，成长路径（如架构师培养），认可文化（技术分享主导权）
- 回答例子： DOT项目对技术骨干来说，充满挑战和机遇。通过打破职级限制，给技术骨干承担重要工作的机会。比如团队需要一位和PO频繁沟通，并提出技术方案的角色。我们安排了一位Vendor员工，既认可了其在团队重点重要性，又增加了其在global的曝光度。使其变成不可或缺的角色，提升职业安全性角度（保留未来转正的可能性）。 有一个很重要的功能，但是团队已经没有额外的精力来完成它，我们安排了一位轮转来的校园毕业生，她正在寻求升职机会。虽然这个任务对其有一定的挑战，但是只要提前和PO沟通好需求，给出相对稳定的方案，她完成实现部分是不成问题的。PO非常感激这位同事的贡献，在有限的时间内，完成了一个高价值功能。对外完美的展示了团队的灵活性，对于该同事，也证明了其在关键时刻能够帮团队赢得荣誉。

### Q8 如何平衡业务需求和技术债务
- 考查点： 战略权衡能力
- 回答思路： 量化技术债务对业务的影响 + 与业务共创解决方案
- 回答例子： DOT有replatforming, reachitecture 和 refactoring 三大解决技术债务的方法。它们都是基于业务的影响来决定其优先级的。在落地实施的时候，尽可能和业务靠拢，利用解决现有问题，或者实现新需求的机会，穿插式解决技术债务。同时和业务透明沟通，让其理解技术债导致的开发时间会比预期的多一些。

### Q9 资源不足时如何安排优先级
- 考查点： 决策逻辑
- 回答思路： ROI评估（客户价值和战略对齐）+ 最小化风险（如合规需求优先）
- 回答例子： DOT项目有众多的需求，需求本身有一定优先级和先后性；另外还有一些需求是合规要求，不完成无法交付，必须优先实现。
